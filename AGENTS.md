# AGENTS.md

This file provides guidance to AI coding agents in this repository.

## Project state

Ieakaso is mostly at the design stage: the product runs through the `/ieakaso` skill (see Commands). The Python package in `src/ieakaso/` holds the CV parser, the Job ad fetcher, the tracker, the viewer, the usage display and the development tools.

- **Toolchain:** Python 3.14 managed by `uv`. Dependencies live in `pyproject.toml`; add them with `uv add` (or `uv add --dev` for development-only ones).
- **Tests:** `uv run pytest` (pytest, in `tests/`). CI (`.github/workflows/ci.yml`) runs `ruff check` and pytest on every push and PR to `main`. Tests run on temporary fake repos; never let a test write to the real `input/`, `output/`, `config.yml`, `db/`, or `~/.config/ieakaso/`.
- **CV parser:** `src/ieakaso/cv_parser/` turns the Source CV into the Parsed CV `input/parsed-documents/cv.md`, and the LinkedIn profile init recorded into its Parsed document `input/parsed-documents/linkedin.md` (`documents.py`; terms in `CONTEXT.md`, decisions in `docs/adr/0001-deterministic-cv-parser.md`, `docs/adr/0004-parsed-documents.md` and `docs/adr/0006-input-split-by-who-writes.md`). `input/candidate/` is written by the candidate, `input/parsed-documents/` by Ieakaso, and `src/ieakaso/layout.py` holds the paths. It is deterministic code, never the agent. Its expected outputs in `tests/fixtures/expected/` are the spec: when output changes, regenerate them with `uv run python tests/fixtures/update_expected.py --all`, review the diff, and raise `PARSER_VERSION` in the same commit. Fixtures are synthetic or anonymized CVs only; the repo is public.
  - **CV versions** (`versions.py`, `docs/adr/0005-cv-versions.md`): `input/candidate/documents/cv/` is an inbox. A new file is identified by its SHA-256, never its name, and moved (not copied) into `input/candidate/documents/cv/cv_<yyyy-mm-dd>[_n]/`, a folder that holds only the candidate's file; the frozen copy of its Parsed CV goes to `input/parsed-documents/cv-versions/<version id>.md`; the version goes to `cv_versions` in the tracker (the parser imports its operations, it never writes the db itself). The label defaults to the file name without its extension. Content that matches a version is reported and left where it is; a folder the parser didn't create gets one warning, recorded in `documents.cv.ignored_folders` of `db/system_status.json` until the folder is gone, and is otherwise ignored. A `PARSER_VERSION` bump regenerates `input/parsed-documents/cv.md` and leaves the frozen copies alone. Every new file is asked about, even the first CV (the mode offers main CV or not a CV, no Tailored CV while there are no Applications); only a Source CV lying directly in the inbox that was recorded and parsed before CV versions becomes the first version without a question, dated by `documents.cv.parsed.parsed_at`, and the records with `applied_on` set are linked to it.
  - **Command:** `uv run python -m ieakaso.cv_parser [--main FILE | --tailored FILE --for <Application ID>] [--force]`. What the mode asks the candidate (new main CV, Tailored CV for one Application, or not a CV; which of several new files is the main one) comes back as flags. Exit codes: 0 written or up to date, 1 a CV can't be parsed, 2 no CV or setup missing, 3 `input/parsed-documents/cv.md` was edited by hand (diff printed; `--force` overwrites), 4 new CV files wait for the candidate's choice (stdout: a `New CV file: <path>` line each; the Parsed CV was still written), 5 the tracker db can't be used or changed while capturing (nothing moved), 6 a flag names a file not waiting in the inbox or an unknown Application. Other stdout lines: `Captured <id> (<label>) ...`, `Duplicate: <path> ...`, `Warning: <folder>/ ...`. The exit code reflects the CV alone (1, 2, 3 win over 4); the other documents print warnings and never block. The cv-parser mode acts on them (`ai/skills/ieakaso/modes/cv-parser.md`). Tests inject the repo root and `today`.
- **Job ad fetcher:** `src/ieakaso/job_ad/` reads a Job ad from a URL when WebFetch can't: `uv run python -m ieakaso.job_ad fetch <url>` writes the ad as Markdown to stdout, first line `Source: structured data` (a schema.org `JobPosting` in ld+json), `Source: structured data + page text` (the same plus a `## More from the page` section with the page's other readable text) or `Source: page text`, then `Page title: <title>` when the page has one. Exit codes: 0 ad written, 1 fetch failed, 2 login wall or closed ad, 3 no ad content; the job-analyzer mode acts on them, and asks the candidate before using it. It is deterministic code like the CV parser: one GET, no JavaScript, no login, no cookies, one retry, never candidate data. Its expected outputs in `tests/fixtures/job_ads/expected/` are the spec: when output changes, regenerate them with `uv run python tests/fixtures/job_ads/update_expected.py --all` (no network; without `--all` it writes only missing ones), and review the diff. Fixtures are synthetic pages, or Sample pages in `tests/fixtures/job_ads/samples/`: real Job ad pages saved from the web and anonymized (public repo), whose expected outputs in `samples/expected/` are written by hand, hold what the agents need from the ad, and are never regenerated; `tests/test_job_ad_samples.py` checks that every expected line appears in the fetcher's output in order (other page text around it is fine), ignoring Markdown syntax, and a Sample the fetcher can't match yet is a strict xfail. Tests inject the HTTP call, never touching the network. Agents never fetch Job ads with `curl` or `wget`.
- **Tracker:** `src/ieakaso/tracker/` is the only reader and writer of `db/ieakaso_db.json` (model in `docs/database.md`, which is kept in sync with its schema). Deterministic code like the CV parser; agents never edit the JSON. It validates records, writes atomically (temp file + rename), creates the file on its first write, refuses to save over a file it couldn't read as valid JSON, and raises `ConflictError` when the file changed on disk since it was read. `uv run python -m ieakaso.tracker upsert [--json <payload>]` (payload on stdin otherwise) creates or updates the record of a Job analysis, following the re-run rule in `docs/database.md`, and prints `created <id>` or `updated <id>`; `set-cover-letter <id> <path>` sets the Cover letter path, `set-company-research <id> <path>` the Company research path, `set-evidence-bank <id> <path>` the Evidence bank path (`evidence_bank`; a later `upsert` never touches it), and `set-screening-prep <id> <path>` the Screening prep path (`screening_prep`; likewise). `add-contact <id> --type <contact type> --name <name> [--linkedin <url>] [--email <email>]` appends a contact and prints `added contact to <id>`, or `contact already on <id>` (exit 0, nothing changed) when one with the same name or LinkedIn URL is there; `set-status <id> <status>` sets the Application status (the viewer's rules) and `show <id>` prints a record as JSON; the recruiter-screening mode calls all four (issue #77). `set-personal-motivation <id>` sets the Application's Personal motivation (the record's `personal_motivation`, string or `null`; text on stdin, trimmed, prints `personal motivation set for <id>:` and the stored text; empty text or a terminal on stdin is exit 1; `--clear` removes it and refuses text on stdin) and `personal-motivation <id>` prints it, or nothing when there is none; only the cover-letter mode writes it (Step 2c), and a later `upsert` never touches it (`docs/adr/0007-personal-motivation-in-the-tracker.md`). Exit codes: 0 done, 1 invalid payload or path, 2 the db is not valid JSON (left alone), 3 the file changed while the command ran, 4 no such Application. The job-analyzer and cover-letter modes call it; `db/ieakaso_db_example.json` is a valid example, checked by the tests. `uv run python -m ieakaso.tracker cv-versions` and `applications` list the CV versions and the records (tab-separated), `set-cv-version <id> <version id|none>` sets the CV version an Application was sent with, and `set-cv-label <version id> <label>` a version's label; capturing a version is the CV parser's job. The db holds the top-level `cv_versions` list and each record's `cv_version`; the current version is derived, never stored, and `applied` fills an empty `cv_version` with it like it fills `applied_on`. A change to the record's keys raises `SCHEMA_VERSION` (`schema.py`) and adds an upgrade from the previous version to `_migrate` in `store.py`, applied on load; list it under Schema versions in `docs/database.md`. Tests inject the repo root and `today`, and use temp dbs, never the real `db/`.
- **Cover letter assembler:** `src/ieakaso/cover_letter/` builds the Cover letter and the review log from the Round files, so no draft or Review text enters the main conversation. `uv run python -m ieakaso.cover_letter assemble <id> --rounds <n> --final <n> --exit "<Exit>" --reason "<reason>" --motivation used|none [--requested <n> ...]` reads `output/applications/<id>/rounds/plan.md` (the Letter plan), `round-<n>_draft.md` and `_review.md` plus the Job ad file and Company research, writes `<id>_cover-letter.md` and `<id>_cover-letter-review.md` (with a Letter plan section, and each Round's Adapted for voice and Plan departures from the Applicant's notes), and prints the letter. `--exit` takes one fixed value, "3 Rounds" among them. Exit codes: 0 written, 1 the Letter plan is missing or empty, a Round file is missing or unusable, or a Round number is out of range (nothing written), 3 the Application or its Job ad file is missing, or its Company research file is unreadable. `--motivation used|none` is required: it is the header's `**Personal motivation:**` value, from the mode, which knows whether it passed one to the agents; the assembler never reads the tracker. Deterministic code; tests use fake repos and an injected `today`.
- **Evidence bank stamp:** `src/ieakaso/evidence_bank/` keeps an Evidence bank's Sources section, so the agents can work from the bank instead of the Personal knowledge base (`docs/adr/0008-evidence-bank.md`). `uv run python -m ieakaso.evidence_bank stamp <id>` writes, at the end of `output/applications/<id>/<id>_evidence-bank.md`, every Personal knowledge base file the bank is built from with its SHA-256 (`source_files` in `sources.py`: `config.yml`, the Parsed CV, the LinkedIn profile's Parsed document and the candidate's memory files; not `writing-style.md`), replacing an old section; `check <id>` prints `evidence bank is current for <id>` or one `Changed:`, `Added:` or `Removed:` line per difference. Exit codes: 0 stamped or current, 1 stale, 2 no bank file or no Sources section, 3 no Application folder. job-analyzer writes the bank and stamps it; cover-letter checks it (Step 2d). Deterministic code; tests use fake repos.
- **Letter context:** `src/ieakaso/letter_context/` builds the parts of the Job analysis and the Company research the Cover letter agents read, so they read neither in full (`docs/adr/0011-letter-context.md`). `uv run python -m ieakaso.letter_context build <id>` writes `output/applications/<id>/<id>_letter-context.md`, overwriting it: the Job analysis's Strengths, Weaknesses, Screener risks, CV under-sells and Gaps to close, and the Company research's usable company facts (At a glance, Domain and product, Latest releases, Financial moment and Culture, without items from a search snippet or "Not found"), each fact tagged "older than 6 months" or "undated" when it is; never Red flags, Employee reviews, Role impact, Notes or Sources. A missing section prints a `Warning:` line and never fails. Exit codes: 0 written, 1 written without company facts (no Company research, unreadable, or no usable fact; reason on stderr), 3 no Application folder or no Job analysis (nothing written). cover-letter builds it in every Run (its Step 2f); it is not in the tracker. Its parsing follows the templates in `ai/skills/ieakaso/modes/job-analyzer.md`: change both together. Deterministic code; tests use fake repos and an injected `today`.
- **Candidate answer:** `src/ieakaso/candidate_answer/` appends the candidate's own answer to a question about a missing fact to one of their memory files, word for word, after they chose "Add it" for that exact text (`docs/adr/0010-candidate-answers-written-with-permission.md`). `uv run python -m ieakaso.candidate_answer append <file name> <id>` (text on stdin) writes it at the end of `input/candidate/<file name>` under `## Added <yyyy-mm-dd> (<id>)`, creating the file if missing, and prints `answer added to <path> for <id>`. Only `professional-experience-extended.md`, `presentation.md` and `professional-self-reflection.md` take an answer. Exit codes: 0 appended, 1 no text on stdin, 2 a file that can't take an answer, 3 no Application folder; nothing is changed on an error. The cover-letter mode calls it (Steps 2e and 7); it is the only way Ieakaso writes in `input/candidate/`. Deterministic code; tests use fake repos and an injected `today`.
- **Viewer:** `src/ieakaso/viewer/` is a Textual app (`ieakaso-view`, or `uv run ieakaso-view` from the repo; opened by the `viewer` mode in a new terminal window) over the tracker: table (with a CV column: the label of the CV version sent), detail screen with immediate saves (a CV version picker, a Tailored CV only on its own Application; the Personal motivation is shown read-only), the CV versions screen (key `v`) to edit labels, the No answer suggestions, opening the Job ad, Job analysis, Cover letter, Company research and Screening prep. It edits records and never creates or deletes them, and every write goes through the tracker module. Tests drive it with Textual's pilot (`pytest-asyncio`, auto mode) on temp dbs, with the document opener injected. `ieakaso-view` runs in the current terminal from any folder: `locate` in `src/ieakaso/repo/` picks `--root`, else the repo at or above the current folder, else the remembered repo, and the command exits 2 when there is none, when the remembered repo is gone (leaving its file alone) or when `--root` isn't an Ieakaso repo; `tests/test_viewer_cli.py` injects the folder, the config folder and the launcher (`docs/adr/0013-remembered-repo-outside-the-repo.md`).
- **Remembered repo:** `src/ieakaso/repo/` finds the repo (`find_root`) and remembers it for `ieakaso-view` in `$XDG_CONFIG_HOME/ieakaso/repo.toml` (`~/.config/ieakaso/repo.toml` when unset), one key, `root`. `uv run python -m ieakaso.repo remember [--replace]` writes it and prints `remembered <root> in <file>`. Exit codes: 0 written or already the same (a remembered repo that is gone is overwritten), 1 can't write the file, 2 not inside an ieakaso repo, 4 a different repo that still exists is remembered (left alone; `--replace` overwrites). init runs it on every run and asks the candidate on 4; it is not a setup item. The cleaner leaves the file alone. Tests pass the config folder in, never touching `~/.config`.
- **Development tools** live in `src/ieakaso/devtools/` and are never exposed to the candidate: not an `ieakaso` command, not a `/ieakaso` mode.
  - Cleaner: `uv run python -m ieakaso.devtools.cleaner clean [--applications]` returns the repo to a fresh state, or with `--applications` to the Set-up state (terms in `CONTEXT.md`; `--applications` deletes the tracker's temp files and `output/applications/`, and empties the records of the tracker db but keeps its `cv_versions`, deleting the db only when it has none), so init, or a mode, can be tested from scratch. It always backs up what it deletes to `~/.ieakaso-backups/` first, in a timestamped folder; there is no restore, copy files back by hand. Options: `--dry-run` (show what would happen, change nothing), `--root` (default: found from the current folder), `--backup-dir`. Called from Python, `clean()` only backs up when given a `backup_dir`. If you add user data anywhere, add it to the cleaner and `.gitignore` together; `tests/test_cleaner_drift.py` fails when they disagree.
  - Estimate backtest: `uv run python -m ieakaso.devtools.estimate_backtest [session-id | transcript.jsonl ...] [--all]` checks the usage display's output estimate on messages whose output count is known: each final message is left out, estimated from the Session's others, and compared. About 80% in range and a small median error mean the estimate is sound; if not, remove the estimate rather than tune it to one Session.
- **Usage display:** `src/ieakaso/usage/` derives each Run's Token usage, models and Context fill from the Claude Code transcript (nothing is saved). `uv run python -m ieakaso.usage start <mode> | summary | statusline`: the router runs `start` as the Run marker and `summary` when a mode ends; the status line is `statusLine` in the tracked `.claude/settings.json`. Tests use fake transcripts only (`tests/usage_fakes.py`), never `~/.claude`. Context window sizes live in `CONTEXT_WINDOWS` in `report.py`. Background Agent runs often leave a message without its final line, so its output count is a mid-stream snapshot; such output is estimated from the visible characters, calibrated on the Session's final messages, and shown as `~X (low–high)` (`_estimate_outputs` in `transcript.py`).

## Requirements (source: `docs/flows.excalidraw`)

- **Runtime:** runs locally, driven from a coding-assistant CLI (Claude Code, OpenCode) rather than its own UI.
- **Storage:** file-based: Markdown files in a structured folder tree, and the applications tracker `db/ieakaso_db.json`. Each Application's files live in `output/applications/<application-id>/`, a folder that never moves; its status is a field of its record in the tracker (`docs/adr/0003-application-status-in-the-db.md`).
- **Memory:** on first run, the user provides their CV, a professional "about me", key projects, and biggest achievements. The agent should compound learnings from each application process back into memory.
- **Agents:** an *Applicant Agent* that writes the drafts and a *Seasoned Recruiter* that reviews them. A third role, the *Job Application Assistant*, is the main conversation: it starts the two agents and passes work between them (`docs/adr/0002-job-application-assistant-in-main-conversation.md`). A *Company Researcher* (Sonnet, web tools only) researches one topic of a Company research; the job-analyzer mode starts four in parallel and assembles them, and the recruiter-screening mode starts two more topics (Interviewer, Compensation) for the Screening prep. Role files are in `ai/agents/`; the Applicant, the Recruiter and the Company Researcher have pointers in `.claude/agents/` and `.opencode/agents/` (the same agents and targets in both, checked by `tests/test_agent_pointers_drift.py`, which also checks that the usage display counts exactly those agents, `IEAKASO_AGENTS`), the Assistant never does. The Applicant drafts by, and the Recruiter reviews against, the Cover letter guidelines in `ai/skills/ieakaso/general-knowledge-base/` (the General knowledge base; the tech guide next to them is for maintainers, not agents). `tests/test_cover_letter_paths_drift.py` fails when those three files name a tracked file that doesn't exist.
- **Application flow:**
  1. The user pastes a job ad URL.
  2. The `job-analyzer` mode reads the ad and highlights the Job ad's strong and weak points. It is the only reader of the whole Personal knowledge base: after the Job analysis it writes the Application's Evidence bank, the facts the agents write and review from (`docs/adr/0008-evidence-bank.md`).
  3. The same mode decides whether the user is a top applicant (the Verdict), then writes a Company research on the company behind the ad (automatic for Top applicant and Apply, offered for Stretch and Don't apply; reused when less than 30 days old). It never changes the Verdict.
  4. Read the application form.
  5. Prepare an application report.
  6. If the form asks for a cover letter, the Job Application Assistant runs the `cover-letter` mode. It first checks that the Evidence bank matches the candidate's files and writes it again when one changed, then asks the candidate for up to three facts that would close a Must or Knockout gap, adding each answer to their files only with their permission. It then builds the Letter context, the parts of the Job analysis and the Company research the agents need. The Seasoned Recruiter writes the Letter plan: the needs to answer, the evidence for each in the bank's words, the motive, the gap and a word budget. The Applicant Agent drafts the letter from the plan, the bank and the Letter context, runs the Final check on it, and the Recruiter gives it a Review score from 0 to 100. Below 90, the Recruiter lists every item to remove, rewrite and improve with its exact replacement text, a Keep list and any Plan changes, and the Applicant rewrites, keeping the candidate's voice. Each draft plus its Review is a Round. This repeats until the score is at least 90, the Recruiter declares a Plateau, or 3 Rounds have run; the best-scoring draft is kept (`docs/adr/0012-letter-plan-and-direct-reviews.md`).
  7. Suggest next steps.
- **Interview prep flow:** a second flow, started with the `recruiter-screening` mode (issue #77). It writes the Screening prep for an Application's recruiter screening itself, in the main conversation, in one pass with no Review loop (it does not load the Job Application Assistant role, whose rule is to manage, not write): from the Evidence bank (checked as in cover-letter Step 2d), the Job analysis, the Company research (reused under 30 days, otherwise job-analyzer's R steps), `config.yml` and `writing-style.md`, plus two Company Researcher topics only it runs, Interviewer and Compensation. It adds the Interviewer as a contact, offers the Interviewing status, records the path, and offers a mock screening as a follow-up. The hiring-manager and later stages are not designed yet.

## Commands

All commands go through one skill, `ai/skills/ieakaso/` (loaded through the pointer `.claude/skills/ieakaso/SKILL.md`): `/ieakaso <mode> [args]`. Each mode is a file in `ai/skills/ieakaso/modes/`. The skill description lives only in the pointer; update it there when modes change.

- **Mode entries** (see `CONTEXT.md`): each mode also has a pointer that routes through the skill as that mode: `/ieakaso:<mode>` in Claude Code and `/ieakaso-<mode>` in OpenCode. A new mode touches five places: its mode file, the mode table in `ai/skills/ieakaso/SKILL.md`, the skill description in the pointer, `.claude/skills/ieakaso/skills/<mode>/SKILL.md` (with `disable-model-invocation: true`, so Claude itself only routes through `/ieakaso`), and `.opencode/commands/ieakaso-<mode>.md`. Each mode entry's description is `Ieakaso <mode>: ` plus the table's "Does" text, and the Claude one's `argument-hint` is the table's "Arguments" (OpenCode commands have no argument hint field). `tests/test_mode_entries_drift.py` fails when they disagree.
- **Commands in the docs:** `tests/test_doc_commands_drift.py` fails when a doc (README, AGENTS, CONTEXT, `docs/`, `ai/`, `.claude/`, `.opencode/`) names a `uv run <name>` that isn't a script or dependency in `pyproject.toml`, or a `python -m ieakaso.<module>` that can't run. Rename a command and its docs together.
- **CLI exit codes:** `tests/test_cli_docstrings_drift.py` fails when a module under `src/ieakaso/` with a top-level `main` has no `Exit codes` sentence in its docstring, or doesn't name there a code `main` returns.
- **Claude Code plugin:** `.claude/skills/ieakaso/.claude-plugin/plugin.json` makes that folder a project-local plugin, which is what gives the `ieakaso:` prefix. It loads only in a trusted folder and only when Claude Code starts at the repo root; `claude plugin validate .claude/skills/ieakaso` checks it.
- **OpenCode:** reads the pointer `.claude/skills/ieakaso/SKILL.md` as a skill; its `metadata: opencode/slash: "true"` is what makes `/ieakaso` a slash command there. Keep it.
- **First run:** every mode except `init` checks `db/system_status.json` first and runs `/ieakaso init` if setup is missing or incomplete. `init` is idempotent.
- **User data:** `config.yml` (candidate data, format in `config_example.yml`), `db/system_status.json` (setup state, starting point in `db/system_status_example.json`), `db/ieakaso_db.json` (the applications tracker; model in `docs/database.md`), and the contents of `input/` and `output/` are gitignored and stay on the user's machine. Outside the repo, `~/.config/ieakaso/repo.toml` holds only the repo's path for `ieakaso-view` (ADR 0013); it is not candidate data, and the cleaner leaves it alone. Inside `input/`, the candidate writes `input/candidate/` (Ieakaso only appends their own answers to the memory files, with permission each time: ADR 0010) (the Source documents in `documents/`, and `presentation.md`, `professional-experience-extended.md`, `professional-self-reflection.md`, `writing-style.md` and the optional `deliberate-differences.md`, see Deliberate difference in `CONTEXT.md`) and Ieakaso writes `input/parsed-documents/`, which the candidate never edits. The only mandatory document is the CV: saved in the inbox `input/candidate/documents/cv/`, it becomes a CV version in its own folder there.

## Product guardrails

The tool drafts and the user acts. It never submits applications or sends emails, and it never adds facts about the candidate that the Personal knowledge base doesn't hold; it only reformulates them. Reviews only suggest changes backed by the Evidence bank, which quotes the Personal knowledge base; anything else becomes a question for the candidate. The Applicant Agent and the Seasoned Recruiter never read the Personal knowledge base beyond the Evidence bank, the Parsed CV (the Recruiter), `config.yml` and `writing-style.md` (both: the Recruiter writes replacement text in the candidate's voice, and takes no facts from it); `tests/test_evidence_bank_drift.py` checks their INPUTS. A letter's claims about the company come only from the Job ad and the Company research's public, fetched facts, which reach the agents through the Letter context (never its red flags or employee reviews), and the Review checks them like claims about the candidate. It advises against applying when the score is below 4.0/5, but the user can override that. Research on an Interviewer covers only their public, professional facts; their LinkedIn page is never fetched.

## Agent Skills Settings

- When the human invokes `/grill-me` or `/grill-with-docs`, use the Claude Opus model. This phase requires deep reasoning to map out the complete design tree, capture hidden requirements, and write the specification.
- When the human invokes `/implement`, use the Claude Sonnet model. This phase relies strictly on the pre-generated static markdown context (`docs/agents/`) to build code following test-driven development (TDD), optimizing for fast context-window compliance.

### Domain docs

Single-context: one `CONTEXT.md` plus `docs/adr/` at the repo root. See `docs/agents/domain.md`.
